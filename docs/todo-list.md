## 🧭 메시지 처리 아키텍처 개요 (최종 구조)

```text
              [ Redis (HOT) ]
                    ↓ (TTL 1h or count > N)
            ┌─────────────────────────┐
            │                         │
      [ Worker (마스터 서버) ]       [ Worker (조회 서버들) ]
            │                         │
     ┌──────▼──────┐         ┌──────▼──────┐
     │ RocksDB (WARM) │ ← API → │ RocksDB API Proxy │
     └──────┬──────┘         └──────────────┘
            │
       (TTL 1일 또는 배치 기준)
            ↓
    [ NAS / OBS (COLD) ]
         - gzip batch files
         - 저장만, 거의 조회 없음
```

- **HOT**: Redis 기반 실시간 처리, TTL 또는 수량 기준 WARM으로 이동
- **WARM**: 마스터 서버의 RocksDB에서 관리, API를 통해 다중 서버에서 조회
- **COLD**: 로컬 NAS 또는 Object Storage에 gzip 파일로 저장, 장기 보관
- **장점**: 빠른 조회 + 데이터 보존 + 운영 단순화 + 일관성 유지

## ✅ 구현 항목 체크리스트 (WARM: RocksDB, COLD: Local Disk 적용 기반)

### 🔥 HOT 계층 (Redis)

- [x] Redis List에 메시지 저장 및 시간 인덱스 (ZSet) 구성
- [x] TTL 기반 자동 만료 또는 개수 기준 이동 트리거 구현

- [ ] Redis 장애 시 데이터 손실 방지 (AOF/RDB 백업)

- [x] TTL 만료 정책 적용 (default TTL or 만료 스케줄링)
